# Adapter Design

Why generated adapters take the shape they do. `.ai/` is canonical; every file described here is
generated by `ai sync` and must never be hand-edited.

## The problem adapters solve

Each tool decides for itself what it reads and when. A file the plane considers authoritative is
only authoritative if the tool actually loads it. Adapter design is therefore mostly about
**reachability**, not content: the same canonical rule has to arrive somewhere each tool is
guaranteed to look.

## Always-loaded entry points

Every supported tool gets one generated file at the repository root, because that is the one
location each of them reads without being asked:

| File | Tool |
| --- | --- |
| `AGENTS.md` | Codex and other generic coding agents |
| `CLAUDE.md` | Claude Code |
| `GEMINI.md` | Google Antigravity |

`GEMINI.md` targets **Antigravity project behavior**, not Gemini CLI user memory and not any global
Gemini path. No stable Antigravity-specific location has been documented that differs from a
repository-root `GEMINI.md`, so the adapter uses the same root-file pattern as the other two and
states its target explicitly rather than guessing at a private path.

Each entry point carries a catalog rather than the full text of every rule. The catalog gives a
title, a one-line summary, and a path, so an agent opens the two files a task needs instead of
paying for the whole corpus on every turn.

## Conditional support trees

Two generated trees hold content a tool loads situationally:

```text
.agents/rules/     .agents/skills/     .agents/workflows/
.claude/           (commands and workflows)
```

Any other generated folder under `.agents/` is removed by `ai sync`.

## Activation is part of the contract

A conditional rule is only conditional if the tool can tell **when** to load it. Antigravity decides
that from frontmatter on the rule file itself — `always_on`, `model_decision`, `glob`, or `manual`.

The plane strips its own registry frontmatter (`id`, `type`, `domain`, …) from generated rules,
because that metadata is for the registry and means nothing to the tool. For a long time nothing was
written back in its place, so every rule arrived with **no declared activation at all** and the tool
was free to skip all of them. The visible symptom was an agent that appeared to ignore the rules.

An integration therefore declares its native activation vocabulary in its manifest
(`rule_frontmatter`), and the renderer emits it. The generic core knows the *concept* of activation;
the manifest owns the *spelling*. Two details are load-bearing:

- The emitted description is **quoted**. A rule summary routinely contains a colon
  (`Rule: Task Contracts`), which unquoted would break the tool's parse of the whole frontmatter
  block and silently return the rule to being ignored.
- Deprecation stubs declare `manual`, so a stale path still resolves to a pointer without spending
  always-on context.

## Consequences

- Entry points grow over time, because reachability is worth more than brevity for a file that is
  always loaded. Keep the catalog terse; keep the rules themselves in `.ai/`.
- If a tool documents a different project-prompt path, update its manifest under
  `scripts/extensions/<tool>/` and regenerate. No core change should be required.
- Adding a tool is a manifest plus templates. It is data, not new rendering code.
